# Consignes pour Claude

- Langue : français pour le code commenté, les messages de commit, les demandes de fusion, l'interface et la documentation.
- Documentation de référence : `docs/specifications.md` et `docs/architecture.md` font foi. Toute modification du périmètre, du comportement ou de l'architecture met à jour ces documents dans la même demande de fusion (y compris le registre des décisions).
- Cycle : une branche et une demande de fusion par évolution, jamais de poussée directe sur `main`. Jp relit et fusionne ; la fusion déploie sur GitHub Pages.
- Demande de fusion : l'ouvrir en brouillon, la mise à jour de `docs/` en premier commit. Sa description commence par `Closes #N` pour fermer l'issue à la fusion : GitHub ne reconnaît que les mots-clés anglais (`Closes`, `Fixes`, `Resolves`), « Ferme #N » ne ferme rien. Elle reste en brouillon pendant que Jp essaie la version de test ; Claude la passe prête à relire quand Jp a fini de valider ses essais (ou Jp la passe lui-même). Une PR qui ne touche pas l'application (documentation, consignes, CI) n'a rien à essayer : elle s'ouvre directement prête.
- Principes à respecter : voir « Principes directeurs » dans les spécifications (le bout de tissu d'abord, physique qualitative, complexité optionnelle, mobile d'abord).
- Architecture : `src/sim` ne dépend de rien ; `session` dépend de `sim` ; seule la session fait avancer la simulation (`tick`) et modifie l'état : `render` et `ui` passent par elle, et n'empruntent à `sim` que ses types, sa géométrie et ses constantes. Pas de syntaxe TypeScript non effaçable (enums, propriétés de paramètres de constructeur) : les tests tournent avec la suppression de types de Node.js.
- Avant de proposer une demande de fusion : `npm test` doit passer, et les comportements physiques modifiés doivent être couverts par un scénario dans `tests/`.
- Tests et catalogue : les tests chargent leurs scénarios de référence dans `tests/situations/`, jamais dans le catalogue, qui évolue librement. Le catalogue n'est testé que sur ses règles, dans `tests/catalogue.test.ts` (présence dans le menu, validité, bittes, aussières vers l'extérieur, gardes croisées, voisins et allée). Un nouveau comportement se couvre par un scénario de référence, pas par une situation du catalogue.

## Environnement de développement de Claude (claude.ai)

Consignes pour les sessions lancées depuis claude.ai, dont l'environnement distant a un accès réseau restreint.

- **Dépôt** : le rattacher avec un accès en écriture (`push`), sinon `gh api` ne voit ni les issues ni les PR. GraphQL n'est pas disponible : `gh issue view` et `gh pr view` échouent, passer par l'API REST (`gh api repos/jppouzol/mini-cassiopee/...`).
- **Clone superficiel** : juste après le clone, lancer `git config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'`, pour que `git push -u` établisse le suivi des branches. Sans cela, une alerte signale à tort des commits non poussés.
- **Registre npm** : accessible depuis octobre 2026. Le vérifier une fois (`npm view react version`), puis installer les dépendances avec `npm ci`, aux versions exactes de `package-lock.json`. Une dépendance ajoutée ou mise à jour passe par `npm install`, et le `package-lock.json` modifié est commité avec elle. S'il ne répond pas, ne pas insister (ni contournement du proxy) et passer au repli ci-dessous : `npm test` fonctionne sans les dépendances.
- **Repli sans registre** : construire avec esbuild et React, dans `/opt/npm-tools/node_modules` :
  `NODE_PATH=/opt/npm-tools/node_modules /opt/npm-tools/node_modules/.bin/esbuild src/main.tsx --bundle --minify --format=iife --jsx=automatic --define:process.env.NODE_ENV='"production"' --outfile=<dossier>/app.js` (produit aussi `app.css`) ; la vérification des types et la construction Vite restent alors à la CI. Le dire dans la PR.
- **PR en brouillon** : l'ouvrir avec `-F draft=true`. L'API REST de GitHub ne permet pas de la passer prête, et GraphQL n'est pas disponible, mais le proxy de la session offre une route pour cela : `gh api -X POST repos/jppouzol/mini-cassiopee/pulls/<numéro>/ccr/ready_for_review` (vérifiée le 15 octobre 2026 sur la PR #47).
- **Avant d'ouvrir une PR** : `npm test`, `npm run typecheck` et `npm run build`, comme la CI. Puis essai de la fonctionnalité dans Playwright pour Python, avec le Chromium de `/opt/pw-browsers/chromium-*/chrome-linux/chrome`, au format téléphone (390 px de large) puis PC, sur `dist/` servi sous `/mini-cassiopee/` comme en production (`npm run preview -- --port 4173`, puis `http://localhost:4173/mini-cassiopee/`), pas sur une maquette.
- **Essai hors ligne** : en plus, quand la PR touche `src/pwa/`, `index.html`, `public/` ou `vite.config.ts`, ou ajoute un fichier chargé à l'exécution (image, police, données) : service worker actif après un premier chargement, puis réouverture hors ligne (`set_offline` du contexte Playwright).
- **Artefact de test** : à chaque PR qui touche l'application, sans attendre que Jp le demande, assembler la page autonome depuis la construction Vite (`node outils/artefact.mjs <page>`, après `npm run build` : JS et CSS de `dist/` intégrés, polices Google en lien) et la publier comme artefact privé, en même temps que l'ouverture de la PR en brouillon. Le republier à chaque nouvelle version de la branche. Il est supprimé une fois la PR fusionnée. Le service worker ne s'y enregistre pas : le hors-ligne s'essaie sur `dist/`.
